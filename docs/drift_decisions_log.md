**D-056 · 2026-07-25 — Ch.2, "The Knowledge Model": domain state, the learning-event evaluator, and three binding C1 amendments.**
MAJOR artifact, AUDITED-GO from C1. Brain-layer only this pass — no new player-facing UI surface (Ch.4 owns the actual reveal); one small existing-UI-copy fix (item 6) is the sole body-layer touch, and it is a wording change to an existing surface, not a new one.

1. **Domain state (`src/brain/knowledge.ts`, `KnowledgeState.domains` in types.ts).** Three scores per domain — Technique, Understanding, Adaptation — across seven domains (Survivalcraft, Foraging & medicine, Harvesting & fabrication, Construction, Mechanical systems, Electrical & radio, Navigation & seamanship). Every score starts at `TUNE.knowledgeInnateFloor` (5), not zero. Four of the seven domains have no producer anywhere in this codebase this pass (Foraging & medicine included, deliberately — see item 4) and will sit untouched for a long time — the ruling's own framing, matched exactly to D-055's forward-compatible-plumbing precedent (`materials.ts`'s family/tag schema): unused runway is not a gap to fill artificially.
2. **The learning-event evaluator (`evaluateLearningEvent`).** A pure function over five factors (challenge, novelty, feedback, consequence, reflection, each 0..1) producing a (Technique, Understanding) delta. Built deliberately MULTIPLICATIVE rather than additive: Technique is gated entirely by `challenge × feedback`, Understanding entirely by `novelty × (a reflection/consequence blend)`. **Judgment call, stated plainly:** "repeating an already-mastered action with no new information produces a near-zero delta, by construction, not a special-cased check" is satisfied by this shape specifically — a caller's own factors (`tryFactorsFor`) derive `challenge`/`novelty` as a domain's remaining HEADROOM (1 at the floor, 0 at the ceiling), so a maxed domain gets an exact 0 on both stats with no `if (mastered) return 0` anywhere in the file. Never surfaced to the player as a raw number — internal only.
3. **The existing stub wired for real (D-055's null-outcome journal).** `recordCombinationAttempts` (recipes.ts) now calls `applyLearningEvent` on every genuinely new null pair, using a dedicated `nullOutcomeFactors()` (challenge=0, consequence=0, novelty/feedback near-certain) — a null attempt is a genuine Understanding-ONLY gain in the recipe's own domain, Technique staying at exactly 0 by the evaluator's own construction (nothing was actually made). Each `Recipe` (recipes.ts) gained a `domain` field as the single source of truth for which domain it trains, both for this null-outcome path and for a real craft (item 4).
4. **Existing verbs mapped to domains — narrowly, exactly as named, nothing invented.** `domainForNodeKind` maps ONLY felling (tree), quarrying, and salvage to Harvesting & fabrication; every other `NodeKind` (including `rock` and `crashbox`, both axe-gated, and all of driftwood/deadfall/berrybush/coconutpalm/reed/shellfish) returns `null` — left at the floor, on purpose, matching Foraging & medicine's own "sits untouched" framing rather than an intuitive-but-unstated extension. Shelter/storage/repair map to Construction; drinking/eating/sleeping/fire (build/feed/light) map to Survivalcraft — all as named. **Two judgment calls, stated rather than silently expanded:** (a) `craftAxe`/`craftStoneHammer` (fabrication acts, not named individually) were mapped to Harvesting & fabrication alongside "knapping" (which the ruling does name) — leaving them out while knapping counted would have been an arbitrary inconsistency between three fabrication verbs of the same kind, not scope discipline; (b) `craftTorch` was mapped to Survivalcraft, not Harvesting & fabrication, since the torch is a warmth/fire item by role (matching item 4's own "warmth/fire" bucket), not a harvesting tool.
5. **Five channels, minimally (`LearningChannel` type, knowledge.ts).** `'trying'` is the only channel with a real runtime path this pass — every successful gather/build/craft call site (state.ts, session.ts's `sleep()`) calls `recordTrying` once, and a null-outcome attempt (item 3) is treated as the same channel with a different factor shape. `'teaching'`/`'watching'` exist as TYPE VALUES ONLY — genuinely unreachable in solo play, no UI, no trigger, per D-054's "design multiplayer-shaped, build single-player-first" law. `'foundContent'` is stubbed identically — no source exists until Ch.3. `'innate'` is not a runtime path at all; it IS `freshDomainScore`'s own floor.
6. **Feedback-must-be-perceivable: a real hard-gate found and fixed.** Audited existing tap-fail copy in `game.ts`; found two instances of the flat "requires X" pattern ("You need an axe for that." / "The box is sealed. You need an axe.") that obscured a real, hidden three-step tier chain (stone hammer → knapped blade → wood/fibre) behind one static sentence. Fixed by extracting `axeNearestReason()` — reusing `contextualHint()`'s own pre-existing three-tier logic (previously duplicated, now centralized) — so both tap-fail sites and the idle hint report whichever step is actually blocking right now. **Reviewed and deliberately left alone:** "Needs wood in hand to repair.", "Nothing to store, and nothing to take.", and "Too far from the shelter to sleep." — each names a single, un-tiered condition with no hidden chain behind it; there is no "nearer" reason to give. The convention (name the nearest true reason, not the final gate, whenever a real tier chain exists) is now standing for Ch.4/Ch.6's future UI strings.

**D-055 · 2026-07-25 — Ch.1 v3, buildable content: the null-outcome journal, material families/tags, grades, and the stone hammer.**
Four items, one pass, C1-cleared (no re-audit needed on the design itself — this entry documents what shipped and the judgment calls made building it). No prior spec for this exists in the repo; the ruling itself is the complete spec, the same as every large package this cycle.

1. **The null-outcome combination journal.** One genuine ambiguity was resolved with the director before building: whether "combination attempts" meant a new free-form tap-two-items verb, or an internal check inside the existing Build panel. **Chosen: internal to the Build panel** (director's explicit answer, `AskUserQuestion`). Every recipe is now expressed as a small list of SLOTS (a role — "handle," "blade," "binding" — each requiring a material family or tag, not a hardcoded resource name, `src/brain/recipes.ts`). Opening the Build panel walks every slot against every material kind currently held; a kind that does NOT satisfy a slot is journaled as a null (`slotId|materialKind`) pair and fires a knowledge event, so the identical pair is never re-evaluated — "a repeat attempt against a known-null pair short-circuits to the same free, no-cost outcome instantly." Ch.2 (knowledge/experimenting) does not exist in this codebase yet; the knowledge event is a stub hook only (`KnowledgeEvent`, `state.knowledge.events`), unwired beyond being recorded.
2. **The material family/tags schema (`src/brain/materials.ts`).** Every current material (wood, stone, fibre, berries, coconut, shellfish, the new sharp blade) gets a primary `MaterialFamily` (`organic` | `mineral`) plus tags (`fuel`, `woodwork`, `textile`, `masonry`, `blade`, `food`). Recipes match on primary OR any tag. **Deliberate scoping call:** today's actual crafting costs (axe/torch/shelter/storage/hammer) are UNCHANGED — every slot is written to stay satisfied by exactly one material kind (disjoint tags by design), so re-deriving the existing, already-tested cost-gating through the new slot system would have risked a live path for zero behavioural gain this pass. The schema is genuinely used (the journal above, `materialSatisfies`) — it just isn't yet asked to blend two different materials into one slot, since nothing in the current roster calls for it. Forward-compatible plumbing for a future material (a later chapter's wire/bone-style pair) sharing a family or tag, not a rebalance of what's craftable today.
3. **Grades: crude / serviceable / refined / exceptional.** Rolled once at craft time via a seeded hash (`rollGrade`, the identical determinism technique `deadfallYield`/`spawnSalvageNode` already use — never `Math.random()`), plain stated odds (50/35/12/3, honest-systems law, no loot-box dressing). Exactly one functional stat moves per item type, never more: the axe's fell speed, the torch's burn duration, the shelter's warmth-drain bonus. **`serviceable` is deliberately defined to reproduce every pre-grade constant exactly** — a save migrated to that baseline grade is functionally unchanged from before grades existed. Visual: a small coloured stud on the axe head, the torch haft, and a shelter pole — the same "drawn, not just stated" rule the harvest blaze-mark/depletion-stump system already set, coloured once on the shown/built transition (grade never changes after craft).
4. **The stone hammer — a new Tier-0 craft, live now.** Its one verb: knapping raw stone into the sharp-blade intermediate. Per C1's explicit "no dead-on-arrival tools" rule, a new material with no real consumer would itself be dead-on-arrival — so the axe recipe now consumes a knapped sharp blade instead of raw stone directly, the concrete "unlocks the next tier" the hammer is described as. **An axe already owned before this pass is completely unaffected** — the boolean `tools.axe` isn't re-evaluated; only a fresh craft goes through the new recipe. Knapping itself is repeatable (2 stone → 1 blade), with no "done" state, unlike every other Build-panel entry. **The bandage was explicitly NOT shipped this pass** — no injury/wound condition exists yet to give it a live verb, and C1's ruling was explicit: leave it undesigned, not half-built.

**Save schema bumped v5→v6** (`migrateV5toV6`, `save.ts`): the sharp blade, the stone hammer, and the three grade fields are all new. Every already-owned axe/torch/shelter heals to the baseline `serviceable` grade on load — the honest "we don't know what grade it would have rolled" answer, never a retroactive up/downgrade — and a returning player simply hasn't made a hammer or knapped a blade yet, the same reasoning every migration in this file has used for new content.

**Regression-locked:** `tests/materials.test.ts` (10 new — the family/tag schema, `materialSatisfies`, the journal's short-circuit and knowledge-event behaviour, and a check that every current slot really is satisfied by exactly one material kind); `tests/grades.test.ts` (8 new — `rollGrade`'s determinism and its roughly-correct odds distribution over 20,000 seeds, the exact per-grade multiplier tables, and `serviceable`'s exact reproduction of every pre-grade constant); new stone-hammer/knapping cases in `tests/crafting.test.ts` (6 new, including the full gather → hammer → knap → axe tier end to end); `tests/save.test.ts` gained a v5→v6 migration describe block (4 new). `tools/smoke.mjs` gained a "D-055" section: the stone hammer and knapping crafted via real taps on the Build panel, the axe proven NOT craftable on raw stone alone, the crafted axe's real grade read back, the Build button's visibility gate extended to cover the hammer too, and the null-outcome journal proven through the real UI action that triggers it (opening the panel), with the journal forced empty first rather than assumed — this run's own berry-bush check, much earlier in the same continuous session, had already put berries through the panel once, so trusting "the journal starts empty" here would have been exactly the incidental-leftover-state mistake this file's own lessons already warn against.

**Verification:** purity ✓ (12 brain files, 14 modules — `materials.ts`/`recipes.ts` both newly in the closure), docs-integrity ✓, typecheck ✓, **185 brain tests ✓** (157 + 28 new), production build ✓. Device harness: pre-flight sanitation ran clean; **128/130**, with the entire new "D-055" section passing outright — the stone hammer and knapping crafted via real taps, the axe proven not craftable on raw stone alone, a real grade (`refined`) read back off the crafted axe, the Build button's visibility gate confirmed to now also cover the hammer, and the null-outcome journal proven through the real UI action that triggers it, forced empty first rather than assumed. Getting there took three of this pass's own harness bugs, root-caused and fixed, none in product code: a pre-existing "A4/A7" section still granting raw stone for the axe recipe (fixed to grant a sharp blade directly); the "Build panel shows all N items" count stale at four; and — the sharpest one — an initial "journal starts empty" assertion that was true in isolation but false in the full run's actual incidental state (78 pairs already accumulated from earlier panel opens), followed by a second miss where forcing the journal empty still read back 0 pairs because the Build button itself was correctly hidden (everything already built) and a `realTapDom` call's own `.ok` had gone unchecked — fixed by also forcing the torch back to unowned so the panel stays reachable, and by adding an explicit assertion on the setup tap's own success flag. **D-053 · 2026-07-25 — the vanishing Build button: a stale HUD visibility gate, root-caused fresh, plus a standing harness-sanitation order.**
**Director's live report:** the Build-panel entry button is not appearing on screen at all — "no button, no way to open it" — on his real, long-running save. This blocks shelter/storage/repair/torch: the entire Build-panel surface. The device harness had tapped `.secondary-action` successfully throughout C05/D-051/D-052 without incident, which C1's own ruling correctly flagged as proving only that the element exists in the DOM in whatever state each of those tests happened to run in — never that it stays visible in every state a real save can reach.

**Root cause, confirmed by direct reading, not assumed from the harness's clean record:** `paintHud()` (`src/body/game.ts`) gates the Build button's visibility on `!state.tools.axe || !state.shelter.built || !state.storage.built` — a condition written for C05, before the torch existed. D-052 added the torch as a fourth Build-panel item that same day, and this condition was never updated to know about it. The result: once a player has genuinely built all three of the ORIGINAL three items — exactly what a long real session accumulates — the condition evaluates false and the button's `display` is set to `none` outright, even though the torch sits inside the panel, uncrafted and now completely unreachable. No CSS/z-index/layout defect exists underneath this; the button's stylesheet rule is unconditional, and the only thing hiding it is this one JS-computed inline `display: none`. **Confirmed mechanically why the harness never once caught it:** every scenario in `tools/smoke.mjs` opens the Build panel EARLY in its own run, before axe/shelter/storage are all built — none of them ever exercised the "everything-but-the-torch" state a real long-running save reaches. A selector existing and being tappable in ONE state is not the same fact as a button staying visible across every state — exactly the gap C1's ruling named.

**Fixed:** the condition now also checks `!state.torch.owned`. General, not special-cased — the button's true job ("is there anything left on the panel") now actually matches everything the panel contains.

**Harness gap closed, mandatory, matching the bug exactly:** a real visibility check (`isVisible()`, `tools/smoke.mjs`) — computed style (`display`/`visibility`/`opacity`), a non-zero bounding rect inside the viewport, and occlusion (`elementFromPoint`) — replacing "a tap either landed or didn't" as the only evidence a button is actually on screen. Paired with a screenshot-diff companion (`shotOfRect()`): the SAME fixed screen region (the `.action-row` container, which stays laid out regardless of which child button is shown, not either button's own collapsible rect) captured in two different states, asserting the rendered pixels genuinely differ — so a check cannot pass on a DOM flag alone while nothing visibly changed. Applied to the Build button first, per the ruling; the pattern generalizes to any primary HUD button.

**Standing harness-sanitation order (C1 ruling, made structural — this is the third bench-corrupted run):** a `preflight()` step now runs before anything else in `tools/smoke.mjs`: refuses outright if a git worktree operation is mid-flight (`.git/index.lock` or any `.git/worktrees/*/locked`) — exactly the state that pulled a fresh-context C3 audit's own isolated worktree out from under it mid-pass during D-052; kills stray Chrome processes left over from a prior crashed run (previously a manual `taskkill` this session ran by hand every time the bench got corrupted); and confirms the target URL actually responds before sinking minutes into a Puppeteer launch against a dead server. All three fail loud and refuse to proceed rather than run into a known-bad environment silently.

**Regression-locked** (`tools/smoke.mjs`, section "D-053"): forcing axe/shelter/storage built with the torch still uncrafted confirms the Build button stays visible (`isVisible()`, not a tap); forcing the torch owned too confirms it correctly disappears; a screenshot diff between the two states confirms the change is real on screen. No brain-level state exists for this — it is a pure HUD-computation fix, covered entirely by the harness.

**Verification:** purity ✓, docs-integrity ✓, typecheck ✓, **157 brain tests ✓** (unchanged — this fix lives entirely in the body), production build ✓. Device harness: pre-flight sanitation ran cleanly (no worktree operation in progress, stray Chrome killed, target URL confirmed reachable) ahead of a **116/118** full run — all three new D-053 checks passed, including the screenshot diff. The remaining two misses are the same pair D-051's and D-052's own passes already traced to this machine's CPU contention interacting with a real per-frame delta clamp, reproducing a fourth time with the identical symptom — not a regression, not newly investigated here, consistent with this doc's own standing lesson about naming a verified, repeated, environment-tied cause as noise rather than re-chasing it.

**KEY REPORT to C1:** root cause is a one-line stale gating condition, now general; the mandated visibility-check pattern and the pre-flight sanitation order are both structural, not one-off patches, and the harness is 116/118 clean under them. **Verdict, self-assessed: ready for C3 audit.** *Status: standing.* — C2

**D-052 · 2026-07-25 — Living Island Track A, the immediate FIX package: energy inversion, the death exploit, salvage reachability, depletion visuals split by nature, and the torch.**
Five items, one pass, shipped ahead of any Living Island dossier chapter reaching CODE, per C1's directive. Root causes and fixes:
1. **Energy inversion.** `gatherNode()` never charged energy at all — the ambient per-game-hour drain in `reconcile()` was the ONLY cost that existed, so a felled tree and an idle minute cost identically nothing extra. Fixed: every `hold`-interaction (effortful) node kind now costs a tuned amount on a successful gather (`effortEnergyCostFor` in `state.ts`); every `tap`-interaction kind stays free. `energyDrainPerGameHour` retuned 5→2 so the ambient/idle rate alone is not harder than before now that action costs exist on top of it. Both directions regression-locked independently (`tests/construction.test.ts`), per the handoff's own instruction not to assume one proves the other.
2. **The death exploit (interim only — the full design is a later dossier chapter, not built here).** `respawn()` set every vital to max — a free-refill loop indistinguishable from genuinely eating/drinking/sleeping. Fixed: thirst/hunger/energy now wake at `respawnVitalFraction` (0.5), health lower still at `respawnHealthFraction` (0.3). Warmth is a deliberate exception, kept at max — it is the acute killer (Rule of Threes, charter §I.6) and stacking a second cold-death on the heels of the first is a tradeoff for the death chapter to make, not this fix. Every death is now logged (`trace.deathLog`: cause + game-hour) for the debug export (D-050's tool).
3. **Salvage reachability.** `spawnSalvageNode`'s radius band ran up to `WORLD.islandRadius - 4` (118 m) — up to 10 m past `WALKABLE_RADIUS` (108 m), landing spawns in the shore falloff, in or at the water. Fixed: the band is bounded by `WALKABLE_RADIUS` (minus a shore margin), and a new general-purpose `isWalkablePoint()` (`world.ts`) validates every candidate before it is committed, with a defensive centre-of-island fallback should the formula itself ever be wrong in the future. A pre-existing brain test had a bound loose enough (`islandRadius - 2`) to never have caught this — tightened alongside a new 500-seed property test.
4. **Depletion visuals split by nature.** `NodeViews.sync()` previously shrunk every depleted node except `crashbox`/`salvage` to a 0.32-scale remnant, including driftwood and deadfall — loose, consumed material with no honest "in-between" state. Fixed: driftwood and deadfall now join `crashbox`/`salvage` in the vanish-until-available-again treatment; trees, bushes, rock outcrops, coconut palms, reeds, shellfish, and the quarry keep the existing shrink/stump/sapling regrow, unchanged. A real behavior change, not just an added branch.
5. **The torch — crafting-tree entry #1.** New: wood + fibre → an unlit torch (`craftTorch`); lit only at an active fire (`lightTorch`/`canLightTorch`, reusing the existing interact-radius reach rather than a new one); burns down over `torchBurnGameHours` while lit (closed-form in `reconcile()`, the same treatment as structure decay); spent, not refuelled, once its fuel reaches zero — a fresh one must be crafted. Carried once owned (no equip step, the same "owning it is wearing it" rule the axe already set, D-046(d)): a haft + flame particles + a small point light on the opposite hip from the axe, intensity scaled by night factor like the fire's own light. **D-026 · 2026-07-22 — Audit remediation: the purity check now walks the import graph, and two hit-test numbers moved into `tune.ts`.**
The C3 audit of Cycle 01 (PASS-WITH-NOTES) demonstrated that `tools/check-purity.mjs` only regexed the brain's own files: a brain module importing Phaser *through* an intermediary in `src/data/` passed the check. The brain/body law is the project's one non-negotiable rule (§II.5) and its enforcement was weaker than it looked, so the check was rewritten to resolve and walk the brain's whole transitive import graph and to print the offending chain; the bypass was reproduced, then confirmed caught (exit 1). Also moved: the fire's tap radius (was a literal `40`) and the wood-node tap slack (was in the presentation table) into `tune.ts` as `fireTapRadius` and `nodeTapSlack` — both widen hit targets, so by D-023's own test they change how the game *plays*, not how it looks. The audit's remaining notes (an over-broad test title, two harness checks that could not fail, and a conditional check that could silently skip) were all fixed rather than accepted.
**Second pass, same audit:** C3 then found a *new* bypass on the rewritten checker — `import(parts.join(''))`, a dynamic import with a computed specifier, is working Phaser-loading code that no static analysis can follow. Closed by treating any non-literal `import()`/`require()` inside the brain's closure as a violation in itself: the brain has no legitimate use for one, so the escape hatch is the defect. Reproduced and confirmed caught. C3 also found that the device harness's fire-burn check was flaky (1 failure in 3 live runs) because it compared fuel against a *nominal* three-minute absence while the harness's own reloads leaked real seconds into it — so the check was measuring the harness's punctuality, not the game's arithmetic. Rewritten to assert the invariant instead (whatever time actually passed, the fire burned it at the tuned rate), which tightened the tolerance from ±0.02 to ±1e-6 and made it exact; three consecutive runs, 30/30. Last bare coefficient (`interactRadius * 0.6`) moved to `TUNE.approachStopFraction`. *Status: standing.* — C2

**D-025 · 2026-07-22 — The offline fairness floor is a rule about ABSENCE, not about elapsed time.**
The C3 audit observed that the D-011 warmth floor is gated on a single `reconcile` call reaching the report threshold, so the frame loop's millisecond spans never trigger it: a player who leaves the app gets the floor, a player who sits idle with the screen on does not. Reviewed and **kept deliberately**, because it is the correct reading of D-011: mercy exists for time the player could not act in. Presence is agency; absence is not. Someone watching the fire go out and choosing to do nothing has made a decision, and the charter's fair-challenge test (§I.18 rule 2) is satisfied — it is telegraphed, understandable, preventable, and recoverable. The behaviour is now documented at the gate in `reconcile.ts` and pinned by a test, so it cannot drift silently. **One dependency named explicitly, at C3's insistence:** on the primary device this rule leans on the phone's OS auto-lock, which typically fires inside two minutes of no touches and takes the correctly-floored `visibilitychange` path — so on Android the exposed window is narrow. On a desktop browser (which the charter permits; Android is primary, not exclusive) there is no auto-lock safety net and the gap is fully real. The decision is sound but it is not self-supporting, and Cycle 02 must weigh it on that basis rather than on "presence is agency" in the abstract.
**Flagged for Cycle 02**, where D-011's frame is already the design topic: once warmth carries real stakes, confirm this or replace it with a floor keyed to time since the last interaction. *Status: standing; revisit in C02.* — C2
